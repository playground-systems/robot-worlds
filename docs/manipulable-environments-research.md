# Existing environments with manipulable contents

Checked **2026-11-02** against publisher documentation, source code, dataset cards and distributed license files. This is source research, not a successful import or simulation test. No packages, models or large datasets were installed/downloaded.

**Accepted source policy:** reuse existing simulation-ready environments and supplement them with NVIDIA SimReady assets. The requirement covers usable physics and articulation, not a single asset brand. RoboCasa and MolmoSpaces are approved source families; their import and interaction checks remain to be completed. All modeling, layout and placement decisions follow [the repository's authoring rule](../AGENTS.md).

**Current installed builds:** the three presets below use only NVIDIA SimReady props and furniture. They predate the expanded source policy and are preserved while richer source scenes are integrated.

## Selected scenes

| Scene | SimReady composition | Task families |
| --- | --- | --- |
| **Kitchen** | Original articulated kitchen counter, hollow bowl, recipe books and small props. | Grasp and carry dishware; open, load and close drawers; operate the original hinged door; retrieve stored items. |
| **Factory** | Packing workbenches, storage rack, real drawer cabinet, screwdriver and sealed cartons. | Tool transfer, storage retrieval, drawer pulling/pushing, carton staging and an explicit inspection process cycle. |
| **Living room** | Sofa, coffee table, drawer cabinet, rigid books/notebooks and golf balls. | Tidying, carrying, drawer operation and retrieval. No invented electronics or deformable furniture behavior. |

Astra composes the layouts and task rubrics from prepared source geometry. Original source appearance, articulation and notices are retained; MuJoCo collision adaptations are recorded separately. Room walls and floor markings are ordinary architectural primitives. No non-SimReady furniture, procedural substitute props or microwave from a separate asset collection is included.

The selected industrial [source catalog](../src/robot_worlds/assets/simready/catalog.json) is supplemented by [living-room](../src/robot_worlds/assets/simready/living_room_catalog.json), [kitchen-counter](../src/robot_worlds/assets/simready/kitchen_counter_catalog.json), [dishware](../src/robot_worlds/assets/simready/kitchen_dish_catalog.json) and [workbench](../src/robot_worlds/assets/simready/workbench_catalog.json) catalogs. Each records pinned source files, per-package licensing and conversion evidence. The optimized GLB provider does not declare the exact upstream revision from which its files were derived; our upstream reference check is recorded separately.

The carton is too wide for the current one-handed gripper; the 50 kg pallet is not a TIAGo++ lift task. Books retain their rigid source shape. The conveyor's rollers are passive, so no powered transport is claimed. The inspected optimized catalog did not supply a microwave; the all-SimReady kitchen therefore uses its actual drawers and hinged door instead of promising microwave behavior.

See [manipulation presets](manipulation-presets.md) for the installed scenes, task selection, validation evidence and remaining interaction checks. Native reset and executable rubric checks are separate from a successful robot demonstration. NVIDIA's [physics guidance](https://docs.omniverse.nvidia.com/simready/latest/simready-asset-creation/physics-best-practices.html) describes source metadata; converting it into useful MuJoCo contact behavior remains our responsibility.

## What an import must preserve

RoboCasa's microwave has a physical door joint; power state uses Python logic driven by button contact and door state. An import must preserve both that behavior and task success checks. The official teleoperation demo uses **PandaOmron**; robosuite lists **Tiago**, but compatibility with our TIAGo++ model still needs validation. [Microwave logic](https://github.com/robocasa/robocasa/blob/3443cdf3dd20f9ae8ed41adba442059b506891d0/robocasa/models/fixtures/microwave.py), [teleoperation configuration](https://github.com/robocasa/robocasa/blob/3443cdf3dd20f9ae8ed41adba442059b506891d0/robocasa/demos/demo_teleop.py), [robosuite robots](https://robosuite.ai/docs/modules/robots.html).

MolmoSpaces current main separately documents a G1/SONIC option and Mac CPU installation, but **that newer integration is not established for stable v0.2.9 or for our existing G1 controller**. Its source assets and robot/control packages have separate attribution and dependency requirements. [Current G1 instructions and notices](https://github.com/allenai/molmospaces/blob/22ee21c0fb1d6f2bbccd4a7d5ee6f6dccc488bf1/README.md).

MolmoSpaces' **stable v0.2.9 source confirms physical joint handling**: its scene builder adds a MuJoCo free joint to non-frozen, non-kinematic props and configures actual hinge/slide joints for cabinets, drawers, ovens and dishwashers. Kinematic flags and category-specific exclusions can remove joints. Its iTHOR test script pulls a grasped handle while stepping MuJoCo and measures joint-position change. This is stronger evidence than an animated open action, but it does not inventory the downloaded FloorPlan1 or establish that those tests pass locally. [Stable builder](https://github.com/allenai/molmospaces/blob/735138876887eb64650742631b8dda841dd264bf/molmo_spaces/housegen/builder.py#L949), [stable articulation test](https://github.com/allenai/molmospaces/blob/735138876887eb64650742631b8dda841dd264bf/mlspaces_tests/scenes/ithor_grasp_articulate_test.py#L365).

Recommended implementation sequence, not work performed here: pin a scene and all dependencies; preserve separate objects, mass/inertia, passive joints, collisions, materials and source credits; replace the source robot with our robot and deliberate spawn/controller mapping; expose persistent object/joint identities in the viewer; then verify free-body settling, a cabinet/drawer sweep, gripper contact, placement into a cavity and a navigation-to-manipulation sequence on Mac. Exported object poses should follow simulation state. Rendering a scene successfully is not evidence of any of those physical capabilities.

Standalone **robosuite** is a smaller MuJoCo baseline: `Door`, `PickPlace` and `TwoArmLift` have genuine interaction tasks, but they are task stations rather than complete furnished homes. It officially supports macOS/Linux with or without a GPU; use it for a bounded adapter check if needed. [Tasks](https://robosuite.ai/docs/modules/environments.html), [platform support](https://robosuite.ai/docs/installation.html), [MIT license and included notices](https://github.com/ARISE-Initiative/robosuite/blob/5ce6643f3092639d08f7b0f90ed1c6a84f50552c/LICENSE).

## Existing scene reuse candidates

Rechecked **2026-11-02** after the request to consider modifying existing environments. **RoboCasa for the kitchen and MolmoSpaces/iTHOR for the living room are the recommended candidates.** They already provide composed environments and physical interaction infrastructure. They remain alternatives to the current SimReady-only presets above; neither has been imported, visually matched or physically tested in Robot Worlds.

- **Kitchen: RoboCasa365 L-shaped Island / Farmhouse, layout 4 + style 4.** This is a named complete kitchen; One Wall / Industrial, layout 1 + style 1, is a smaller alternative. Layout/style definitions can change fixtures, arrangement and textures. RoboCasa has actual cabinet door hinges, drawer slides and separately placed movable objects; its door/knob mechanics are distinct from Python appliance state logic such as a burner turning on. Start with cabinet opening and `PickPlaceCounterToCabinet`, rather than promising cooking or fluid simulation. [Named scenes](https://robocasa.ai/docs/build/html/assets/scenes.html), [physical cabinet/drawer implementation](https://github.com/robocasa/robocasa/blob/main/robocasa/models/fixtures/cabinets.py), [interaction distinctions](https://robocasa.ai/), [task example](https://github.com/robocasa/robocasa#basic-usage).
- **Living room: MolmoSpaces `ithor/FloorPlan201_physics.xml`.** AI2-THOR explicitly classifies FloorPlan201–230 as living rooms. MolmoSpaces' current published resource index lists `ithor_FloorPlan201_physics.tar.zst`, and its companion metadata contains `FloorPlan201_physics.xml`; the listed compressed scene archive is **3.157 MB**, excluding separately resolved object dependencies. This verifies an existing MuJoCo conversion, not its exact movable-object/joint inventory. The collection has physical free-body props and articulated fixtures, but kinematic/static exclusions apply; select tasks only after inspecting this scene's actual joints and bodies. `FloorPlan1_physics.xml` is the publisher's explicit kitchen quick-start example. [Room classification](https://ai2thor.allenai.org/ithor/documentation/scenes/), [scene size index](https://huggingface.co/datasets/allenai/molmospaces/blob/main/mujoco/scenes/ithor/20251217_with_occupancy/mjthor_resource_file_to_size_mb.json), [file metadata](https://huggingface.co/datasets/allenai/molmospaces/blob/main/mujoco/scenes/ithor/20251217_with_occupancy/mjthor_resources_combined_meta.json.gz), [MuJoCo quick start](https://github.com/allenai/molmospaces/blob/main/docs/assets.md#assets-quick-start), [stable physical scene builder](https://github.com/allenai/molmospaces/blob/v0.2.9/molmo_spaces/housegen/builder.py).

**Mac and integration:** RoboCasa documents Mac `mjpython` usage and a standard asset download of about 10 GB. MolmoSpaces documents Linux/Mac support, on-demand scene dependencies and stable **v0.2.9**; its Mac debug viewer needs conda/Homebrew Python because the documented `uv` Python lacks the required shared library. Neither requires replacing MuJoCo. Our integration would still need to preserve native scene dynamics/materials, map robot/controller/spawn and object/joint identities, and adapt reset/task hooks into the SDK. This is an integration assessment, not a demonstrated adapter. [RoboCasa setup](https://github.com/robocasa/robocasa#installation), [MolmoSpaces setup and stable-version warning](https://github.com/allenai/molmospaces#installation).

**Modification and redistribution:** RoboCasa declares **MIT code and CC BY 4.0 assets/datasets**. CC BY permits modification and commercial redistribution with attribution, a license link and change notices. MolmoSpaces has **Apache 2.0 code**; its publisher declares **CC BY 4.0 for non-Objaverse data** and **ODC-BY 1.0 for the Objaverse database subset**. Individual Objaverse objects can retain noncommercial licenses, so the database license alone is insufficient. Prefer an inspected iTHOR/THOR-only dependency set for a first bundle. Current main's `commercial_safe` filtering excludes NC content during data generation; benchmark replay remains unfiltered and the feature should not be assumed present in stable v0.2.9. Preserve per-asset notices rather than relabeling source content with our code license. [RoboCasa terms](https://github.com/robocasa/robocasa#license), [CC BY terms](https://creativecommons.org/licenses/by/4.0/deed.en), [MolmoSpaces code/content terms](https://github.com/allenai/molmospaces#license), [per-asset lookup and filtering scope](https://github.com/allenai/molmospaces/blob/main/docs/assets.md#retrieving-per-asset-license-information).

**Factory: NVIDIA UR10 Palletizing is a complete manipulation workcell.** It connects a conveyor, movable bins, flip station and pallet with an existing suction robot/controller. NVIDIA documents physical bin attachment and stacking alignment. This supplies a real industrial workflow, not a whole factory floor. [Current tutorial](https://docs.isaacsim.omniverse.nvidia.com/latest/replicator_tutorials/tutorial_replicator_ur10_palletizing.html), [physical behavior](https://docs.isaacsim.omniverse.nvidia.com/4.5.0/cortex_tutorials/tutorial_cortex_5_ur10_bin_stacking.html), [scene construction source](https://github.com/isaac-sim/IsaacSim/blob/main/source/extensions/isaacsim.robot_motion.examples/isaacsim/robot_motion/examples/manipulation/ur10_palletizing.py).

Isaac Lab **Factory** adds contact-rich peg insertion, gear meshing and nut threading cells. NVIDIA's full warehouse scenes supply buildings and furnishings, but their catalog does not establish working mechanisms or movable stock throughout. None is a verified Mac/MuJoCo import. Isaac Sim requires supported Linux/Windows NVIDIA GPU hardware; its code licenses do not automatically cover referenced assets. Default NVIDIA asset terms restrict modification/redistribution unless separate terms grant permission, so these samples cannot be treated as our already-vetted CC BY SimReady collection. [Factory task configurations](https://github.com/isaac-sim/IsaacLab/blob/v2.3.0/source/isaaclab_tasks/isaaclab_tasks/direct/factory/factory_tasks_cfg.py), [environment catalog](https://docs.isaacsim.omniverse.nvidia.com/latest/assets/usd_assets_environments.html), [requirements](https://docs.isaacsim.omniverse.nvidia.com/latest/installation/requirements.html), [code versus asset terms](https://docs.isaacsim.omniverse.nvidia.com/6.2.0/common/license-faq.html), [asset agreement](https://docs.isaacsim.omniverse.nvidia.com/latest/common/license-isaac-sim-additional.html).

The user approved the recommended household source families and NVIDIA supplementation after this comparison. They are not installed replacements. For a Mac-first factory bundle, retain vetted SimReady assets and compose/test explicit workcells within a dense factory layout. A separately licensed Isaac backend is another integration path, not an existing capability.
